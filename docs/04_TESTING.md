# Этап 4. Тестирование, безопасность, рефакторинг

## Автотесты
```bash
# логика и валидация — не требуют Django и Firebase
python -m unittest core.tests.test_services core.tests.test_validators -v

# HTTP-уровень (регистрация, вход, свайпы, чат, админка, CSRF, ошибки)
USE_MEMORY_DB=1 python manage.py test
```
Покрыто: валидация каждого поля, проверка фото (формат/размер/«не картинка»), дубликат email, хеш пароля,
взаимный лайк → одна пара, дизлайк блокирует пару, повторный свайп, лента (свои/оценённые/заблокированные/предпочтения),
чат (посторонний не читает и не пишет), каскадное удаление, админ-права, блокировка, CSRF, лимит попыток входа, форматы 404/405.

## Проверка безопасности
| Угроза | Что сделано |
|---|---|
| SQL-инъекции | SQL нет вообще; Firestore принимает значения как данные, а не как запрос |
| XSS | шаблоны Django экранируют вывод; весь динамический текст в JS вставляется через `textContent`, не `innerHTML` |
| CSRF | `CsrfViewMiddleware`, токен в `<meta>` и заголовок `X-CSRFToken` на всех изменяющих запросах; тест это проверяет |
| Пароли | PBKDF2-SHA256, 600 000 итераций, соль на каждого; сравнение `hmac.compare_digest`; фиктивный хеш для несуществующего email (нет утечки «есть ли такой email») |
| Перебор паролей | 5 неудачных попыток за 10 минут на пару email+IP |
| Сессии | подписанные cookie, `HttpOnly`, `SameSite=Lax`, `Secure` на проде, `flush()` при входе |
| Доступ к чужим данным | каждая операция чата проверяет, что пользователь — участник пары; публичный профиль не содержит email |
| Загрузка файлов | лимит 5 МБ, Pillow открывает файл как картинку (только JPEG/PNG/WEBP), перекодирование в JPEG, лимит пикселей против «бомб» |
| Права админа | проверка `is_admin` на сервере для каждого `/api/admin/*`; админа нельзя заблокировать/удалить из панели |
| Заголовки | `X-Frame-Options: DENY`, `nosniff`, HTTPS-редирект на проде |
| Секреты | ключ Firebase и `SECRET_KEY` только в переменных окружения, в `.gitignore` |
| Прямой доступ к БД | `firestore.rules` запрещают всё; ходит только сервер через Admin SDK |

Известные ограничения (честно сказать на защите): счётчик попыток входа живёт в памяти процесса;
уникальность email проверяется запросом, а не транзакцией; чат через опрос, а не WebSocket;
ленту собирает сервер из первых 500 активных пользователей — для учебного масштаба достаточно.

## Рефакторинг, который уже сделан
* Вся логика вынесена из view в `services.py` — view только разбирают запрос; логика тестируется без Django.
* Один декоратор `api_view` отвечает за метод, авторизацию, права и единый формат ошибок — нет дублирования try/except.
* Одно хранилище-интерфейс вместо прямых вызовов Firebase по всему коду.
* Правила валидации в одном месте на бэке (`validators.py`) и одном на фронте (`profile-form.js`).
